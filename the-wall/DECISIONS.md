# Decisions

Running log of technical/design choices left open by the brief. Newest at the bottom of each section as they were made during the build.

## Project placement
- Built as `the-wall/` inside the existing `alexdeeley/Beep` repo (the only repo attached to this session), as its own self-contained Node/TypeScript project with its own `package.json` - mirroring how `draw-together/` already lives in the same repo as an independent subproject. Not wired into Beep's own site UI; it's a separate deployable app.

## Stack
- Followed the default stack as specified: TypeScript, Vite (client), Node + `ws` (server), Kysely as the single storage interface over `better-sqlite3` (dev) and `pg` (prod), `@napi-rs/canvas` for server-side rendering sharing client draw code, FFmpeg for video encoding, Vitest for unit tests, Playwright for the multi-client test.
- **Migrations via Kysely's schema builder**, not raw `.sql` files - lets one migration definition target both dialects. The two things Kysely doesn't abstract cleanly are autoincrement PKs (SQLite: `integer primary key autoincrement`; Postgres: `serial`) and the binary column type (SQLite: `blob`; Postgres: `bytea`, since Kysely's dialect-agnostic `"binary"` type name isn't recognized by its Postgres DDL compiler) - both are branched explicitly on dialect in `src/server/db/migrations.ts`, everything else is written once.
- **Kysely over a hand-rolled dual-dialect query layer**: the brief asks for "a single storage interface" behind SQLite/Postgres - a query builder that already understands both dialects is less code and less risk than writing two sets of raw SQL and a dispatch layer.

## Data model
- **JSON payload column** on `operations` (`payload: string`) holding the type-specific fields (stroke's `size`+`points`, pixels' `cell`+`cells`, hide's `targetIds`) rather than a wide table with many nullable columns per type. Keeps the schema simple and portable across dialects; the type-specific validation already happens in `shared/validate.ts` before anything is stored, so there's no correctness cost to not having DB-level column constraints on the payload internals.
- **`seq` is the table's autoincrement primary key**, not a separately-maintained counter - "assign a seq" is just "insert a row," on both dialects, with no separate sequence bookkeeping or race condition to guard against.
- **Idempotency via a unique index on the client id** plus a select-before-insert-fallback-to-select pattern in `insertOperation` - resubmitting the same operation id (e.g. an offline-queued op that actually made it through before the tab closed) returns the existing row instead of erroring or duplicating.

## Tiles
- **Only level-0 tile membership is persisted** (`tile_index` table). Coarser levels are always composed on demand from their four children (recursively, bottoming out at level 0) and cached afterward - avoids a second indexing scheme and keeps "coarser levels are built from finer ones" literally true in the code, not just in spirit.
- **Never-touched tiles are never written to the cache table.** `getOrRenderTile` returns a blank transparent PNG on the fly for any tile with no operations, without persisting it. An "infinite" canvas would otherwise mean the tile cache grows to cover however far anyone has ever scrolled, blank or not.
- **Tile cache invalidation is lazy and seq-based**, not push-based: every tile row stores the highest seq baked into it, and a request compares that to the tile's current true-latest seq (a cheap `MAX(seq)` over `tile_index`, or a recursive max over children for composite levels) before deciding to reuse vs. re-render. `warmTiles()` is called after every commit purely as a latency optimization (pre-warms the cache before the next request), not for correctness - correctness holds even if it's never called.

## Client rendering
- **The exact same `renderOperation`/`renderStroke`/`renderPixels` functions run in the browser and in `@napi-rs/canvas` on the server** (and later, the timelapse renderer) - `shared/draw.ts` defines its own minimal structural `DrawContext2D` interface instead of importing the DOM `CanvasRenderingContext2D` type, since the server build has no DOM lib and both real contexts satisfy the same shape.
- **Level-0 tiles get a live per-op overlay; coarser levels just evict-and-refetch.** A freshly committed operation is drawn directly on top of its level-0 tile's cached bitmap (zero flicker, since that's the zoom level people are actually drawing at) via a small in-memory overlay list keyed by tile. At coarser levels, a new operation just evicts that tile's cached bitmap from the client and lets the next frame re-fetch a fresh server-composited one - simpler than tracking per-op deltas across every level, and the flicker cost is paid rarely, since live drawing is almost always viewed zoomed in enough to be at level 0 anyway.
- **Brush stroke rendering uses the quadratic-through-midpoints technique** (each interior point is a curve control point; the curve passes through the midpoint to the next point) for a smooth path without spline fitting, layered on top of an explicit point-smoothing pass (`shared/smoothing.ts`, a weighted 3-point moving average) applied before points are ever stored - so the smoothing is baked into history and looks identical everywhere it's replayed, not just prettied up at render time.

## Interaction
- **Wheel-vs-trackpad-scroll heuristic**: `ctrlKey` set → treat as a trackpad pinch (this is how Chrome/Safari/Firefox all report it) and zoom toward the cursor. Otherwise, `deltaMode === 0` (pixel-mode) with either a nonzero `deltaX` or a small `deltaY` magnitude → treat as trackpad two-finger scroll and pan; anything else (line-mode deltas, or large pixel deltas) → treat as a physical mouse wheel notch and zoom toward the cursor. There's no fully reliable way to distinguish these from a bare `wheel` event; this is the same heuristic family used by mapping libraries like Mapbox GL and Leaflet.
- **Pan and pinch-zoom are computed from a fixed gesture-start reference** (camera + screen anchor point captured once at gesture start), not incrementally frame-to-frame - avoids any drift accumulating over a long drag or a slow pinch, and makes "the world point under the fingers stays under the fingers" trivially exact rather than approximately true.
- **Inertia is killed unconditionally at the start of every new pointer gesture** (`stopInertia()` is the first thing `onPointerDown` does), which is what makes "panning has light inertia that never carries into drawing" true structurally rather than by tuning a decay constant - the moment any finger touches down again, whatever inertia was still playing is already gone before any draw-vs-pan branching happens.
- **A stroke starts optimistically on the very first pointer contact** (satisfies "draw locally first") and is only retroactively cancelled if a second pointer lands within the 100ms window the brief specifies - rather than waiting 100ms before ever starting to draw, which would put a visible delay on every single-finger touch stroke.

## Realtime protocol
- **The sender never receives its own committed op back** via the `ops` broadcast (explicitly excluded server-side) - it already has the full operation client-side the moment it draws it, and gets the assigned `seq` via `ack`. Echoing it back would mean either discarding a duplicate or (worse) double-applying it.
- **A stroke's `live` broadcast and its final `ops` broadcast are sent in that order on commit**, and the client only records a `live` preview for an operation id it doesn't already know as committed - so a same-tick `live{done:true}` arriving just after `ops` for the same id is a correctly-ignored no-op, not a race to guard against with timestamps.
- **`resync-required` instead of an unbounded backlog**: if a reconnecting client is more than 5,000 operations behind, the server refuses to walk them out one at a time and instead tells the client to fall back to fetching tiles directly (which already contain a full composited history) - keeps a very-out-of-date client's resupply O(visible tiles) instead of O(missed operations).

## Rate limiting & privacy
- **Per-connection token bucket (60 capacity / 30 per second refill) plus a separate per-IP-hash bucket (120 / 40/s)** - sized from "a human's fastest plausible sustained input" (stroke chunks every ~50ms ≈ 20/s, generously headroomed to 30/s) rather than from any specific attack scenario, per the brief's instruction.
- **IP hashing uses a single process-lifetime salt** (from `IP_HASH_SALT` env var, or a random one generated at boot if unset). A random fallback means rate-limit buckets don't survive a restart tied to a specific IP identity across restarts, which is an acceptable cost for a value that exists purely for short-lived rate limiting, never for identification.

## Snapshots
- Interpreted "save the dirty tile rasters together with the seq they include" as: force every level-0 tile that has ever been touched to be freshly rendered and cached, then record a `(seq, created_at)` checkpoint row. Reconstructing the wall at any `seq` is then just "the tile cache as of that point" - which in practice this project already gets from the tile cache's own per-tile seq tracking; the explicit snapshot exists to guarantee a fully-warmed, known-good state exists at round intervals (used by `admin snapshot` and as a sanity baseline for the timelapse/replay consistency check).

## Timelapse
- **Time compression algorithm**: consecutive operations' real inter-arrival gaps are clamped to `[15ms, 4000ms]` before being summed into a monotonic "compressed" timeline, which is then linearly mapped onto the requested frame budget. The floor stretches a burst of literally-simultaneous operations across multiple frames instead of popping them in as one instantaneous frame; the ceiling stops a long idle gap from eating a proportional share of the video. A hard per-frame cap (6 ops/frame in the CLI) is enforced independently of the compressed-time mapping, since a small enough frame budget can still force more than the floor alone would spread out.
- **The per-frame cap always wins over the requested duration.** `buildTimeline` returns as many frames as it needs, never silently dropping the cap to fit a fixed frame count - a pathologically dense burst stretches the video slightly longer than `--duration` asked for (logged to the console) rather than violating "cap operations per frame." The ordinary case (activity spread out realistically) always returns exactly the requested frame count.
- **Point/cell granularity is implemented by exploding an operation into one reveal-event per point/cell** before time-compression runs, each carrying a `prefixLength` truncation, rather than trying to animate sub-operation progress within a single still frame. This reuses the exact same timeline-building code at a finer grain instead of a second, parallel mechanism.
- **`full` mode's camera eases toward a padded bounding box of everything revealed so far** (`lerp` at a fixed 12%-per-frame factor) rather than snapping instantly - a hardcoded ease constant was chosen over exposing it as a flag since the brief only asks for "eases," not a tunable rate.
- **Consistency is verified by actually decoding rendered video frames** (`tests/unit/timelapse.test.ts`), not by trusting the pipeline: it inserts two strokes with distinct colours and a real time gap, runs the real CLI `run()` function end-to-end (spawns real ffmpeg), extracts the first and last frame with ffmpeg, decodes them with `@napi-rs/canvas`, and asserts on actual sampled pixel colours - confirming the earlier stroke is visible before the later one and the final frame contains both. This caught two real bugs during development: `new Image(); img.src = buf` doesn't synchronously decode in this `@napi-rs/canvas` version (only the async `loadImage()` does), and the original `buildTimeline` silently broke its own per-frame cap once `totalFrames * cap` fell short of the event count.

## Admin CLI
- **Backup/restore only needs `operations` + `snapshots`.** `tile_index` and `tile_cache` are pure derived caches (a function of `operations` alone), so a backup is just those two tables as JSON - dialect-agnostic, and restorable onto either SQLite or Postgres. Restore does a raw insert preserving each operation's original `seq`/`ts` (not `insertOperation`, which would reassign both), then explicitly re-syncs Postgres's `serial` sequence afterward, since inserting explicit values doesn't advance it the way SQLite's autoincrement bookkeeping does. Verified end-to-end: backing up the dev database, restoring into a fresh empty one, and diffing a PNG export of each produced byte-identical files.
- **`admin timelapse` is a passthrough to the dedicated `timelapse` CLI** (spawns it as a subprocess) rather than a second implementation, so there is exactly one rendering pipeline to keep correct.
- **`hide`'s bbox is the union of its targets' bboxes**, and it gets tile-indexed into that same region like any other operation - a hide op renders nothing itself, but it still needs to invalidate the cached tiles that contain the content it's hiding, or a stale cached tile would keep serving the hidden mark forever.

## Multi-client acceptance test (`tests/e2e/multi-client.spec.ts`)
- **The spec manages its own server lifecycle** (spawns the Vite dev server and the API/WS backend itself in `beforeAll`, no Playwright `webServer` config) because part 4 of the required scenario needs to actually kill and restart the backend mid-test to prove persistence - something `webServer`'s start-once model can't do.
- **Both clients are pinned to a fixed camera via the URL hash** (`#0,0,1`) instead of relying on the real "frame on recent activity" auto-camera. Two clients loading at slightly different real times could otherwise get subtly different auto-framed viewports, which would break a pixel-level convergence check for reasons that have nothing to do with whether their content actually matches.
- **Tool colour/size is seeded via `localStorage` in `addInitScript`**, not by clicking the palette UI - the two are equivalent (the UI is just a thin wrapper writing the same `wall.tool` key) and this is far less brittle than driving real clicks through the proximity-fade/radial-menu presentation logic that isn't the thing being tested here.
- **Convergence is checked as a tolerant sampled pixel-diff** between the two clients' `canvas.toDataURL()` output, not exact byte equality - real-world encode/blend rounding can differ by a shade even when the underlying operation history is identical, and "converge" means "the same picture," not "the same bytes."
- **Killing the backend for the restart test kills the whole process group, not just the direct child.** `npx tsx ...` (or a plain `spawn("npx", ...)`) interposes a wrapper process that does not forward signals to the real node process it ends up running; sending SIGTERM to only that wrapper leaves the actual server (and its open sqlite connection) alive, which both silently defeats "the server restarts" and - worse - can leave two live processes writing to the same WAL-mode file at once. Fixed by spawning the local `tsx`/`vite` binaries directly with `detached: true` and killing the negative pid (the whole group). This was caught by the test itself: an early version passed by accident (the "restarted" server was actually the never-killed original), then failed once the check for what the *new* process's own read sees was tightened.
- **The timelapse's ordering check scans every extracted frame for each colour's first appearance**, rather than trusting a single hand-picked frame index (e.g. "frame 0") - which real op timing can occasionally miss by one frame without breaking the actual guarantee being tested (that red is revealed strictly before blue).

## Checkpoint 4 critique pass
- **The touch radial palette was broken and got fixed.** It looked plausible in code review (a `.radial` class switching the container to `flex-direction: column`) but a real 390×844 mobile screenshot showed the truth: the swatch row was still exactly as wide as nine 26px circles side by side (~330px), so opening it anywhere near a screen edge - which the corner dot's own position guarantees - pushed most of the colours off-screen. Fixed by actually arranging every button (swatches + sizes + the pixel toggle, 14 in total) around a circle in JS (`layoutRadialButtons` in `ui.ts`, run once since the layout is static) with CSS just anchoring each button via a per-element `--rx`/`--ry` translate, and by clamping the anchor point so the whole circle stays on-screen regardless of where it's opened. This is exactly the kind of bug a code-only review misses and a screenshot catches immediately - which is the entire point of the brief's required checkpoint-4 screenshot check.
- Desktop idle and proximity-fade palette were screenshotted too and matched intent (nothing visible but a faint corner dot at idle; the linear palette fades in near the bottom edge) - no changes needed there.
